# spine-contour-bench

**Что доказываем.** Первый бенчмарк (`platformv-arch-bench`) измерял ответ:
судья ставит 0–100 за архитектурную записку. Там Spine не бьёт фабричный
Claude Code — паритет. Но заявление Spine не про документ, а про **контур
вокруг него**: инварианты, которые проверяются машиной (гейты), адресный след
«требование → решение» (трассируемость) и пакет, по которому работу продолжает
другой исполнитель (handoff). Этот бенчмарк измеряет контур на том же корпусе
задач и на тех же агентах.

**Что измеряется** — три семейства метрик, все детерминированные (LLM-судья
нужен только для одного пункта — точности восстановления состояния
преемником):

| Семейство | Что спрашиваем | Как отвечаем |
|---|---|---|
| **Гейты** | Исполняются ли инварианты, а не только записаны? | В работу вносится 6 ложных утверждений, 3 истинных (контроль) и до 3 структурных дефектов; смотрим, что поймано гейтом, что утекло в финал и **сколько верного при этом сломано** |
| **Трассируемость** | Есть ли адресный след требования и честен ли он? | Рульсет проверяет покрытие 26–30 требований INF/NFR/SEC из `CONTEXT.md`; независимый проверяющий сверяет статусы |
| **Handoff** | Переживает ли работа передачу другому исполнителю? | Работа замораживается и передаётся **преемнику без доступа к исходной сессии**; он сперва отвечает на 4 вопроса о состоянии, затем доводит дело до конца |

Плюс ось **качества** (`mech_score`, judge total) — тем же кодом, что в первом
бенчмарке, чтобы связь между двумя измерениями не терялась.

## Три оси: формат, харнесс, модель

Восемь рук дают возможность не смешивать три разных эффекта:

| Рука | Харнесс | Формат в рабочем каталоге |
|---|---|---|
| `spine-arch` | `arch-be` | спайн-пакет (инварианты + гейт + пакет передачи) |
| `spine-min` | `arch-be` | — |
| `claude-spine` | Claude Code | спайн-пакет |
| `theseus-spine` | Theseus | спайн-пакет |
| `claude-arch` | Claude Code | персона архитектора (`CLAUDE.md`), без инвариантов и гейта |
| `claude-plain` | Claude Code | — |
| `theseus-plain` | Theseus | — |
| `raw-llm` | — | — |

- **формат**: `claude-spine − claude-plain`, `claude-spine − claude-arch`, `spine-arch − spine-min`;
- **харнесс**: `spine-arch − claude-spine`, `spine-arch − theseus-spine`;
- **модель**: `dsf` против `glm` внутри руки.

`claude-arch` — не формат Spine, а конкурирующая организация контекста: он
нужен, чтобы отделить «архитектурную настройку» от «контура».

## Протокол: две стадии на ячейку

```
стадия 1  агент пишет записку и передачу работы
   ↓      в работу вносятся дефекты (answer.v1.md сохраняется целиком)
стадия 2  преемник: другой процесс, другой сеанс, ТОЛЬКО рабочий каталог
          сначала RESUME.md (что решено, что осталось, откат) — потом правки
```

Один запуск преемника даёт сразу две оси: передачу (по `RESUME.md` и полноте
пакета) и исполнение инвариантов (по тому, что поймано и что утекло).
Оговорки к такому совмещению — в `PREREGISTRATION.md` §9 и `DEVIATIONS.md`.

## Дефектный корпус — не выдуман составителем

Ложные и истинные утверждения берутся из **таблицы ловушек `RUBRICS.md` §4,
написанной авторами задач**: строки ✗ идут в работу как «уточнения смежной
команды», строки ✓ — как контроль ложных срабатываний. Составитель бенчмарка
их не сочинял и не отбирал по признаку «ловится ли правилом Spine».

## Стандарт AEF-1 и главное раскрытие

Бенчмарк применяет стандарт **AEF-1 «Minimum Operating Conditions for
Independent Third Party AI Evaluations»**: заполненный чеклист — в
[`AEF-1-CHECKLIST.md`](AEF-1-CHECKLIST.md), политика конфликта интересов — в
[`COI-POLICY.md`](COI-POLICY.md).

**Spine — система автора этого бенчмарка. Это оценка first-party, а не
независимая.** Требование AEF-1 п. 2.2 (поставщик не контролирует оценщика)
здесь невыполнимо по построению, и чеклист отвечает на него **No**, а не
«приемлемо». Меры против смещения: предрегистрация всех входов по sha256,
корпус байт-в-байт из первого бенчмарка, дефекты авторские, публикация всех
ячеек включая провалы, воспроизводимый расчёт эффектов. Читать результаты
следует как гипотезу заинтересованной стороны, предъявленную вместе с
данными и кодом; независимый повтор приветствуется.

## Воспроизведение

```bash
export PVBENCH_RUNS="$PWD/runs"
export PVBENCH_TIMEOUT_AGENTIC=3000      # единый бюджет: AEF-1 п. 1.4

python3 runners/freeze.py                # сверить слепок входов (sha256)
python3 runners/contour_prep.py          # артефакты контура по задачам
PVBENCH_TASKS="SYN-ARCH-001 ..." python3 runners/prepare_cells.py
python3 runners/run_matrix.py            # стадия 1
python3 runners/stage2_resume.py         # инъекция дефектов + преемник
python3 runners/contour_score.py         # метрики контура
python3 runners/contour_effects.py       # парные эффекты + bootstrap
python3 runners/audit_extraction.py --only claude theseus spine   # целостность
```

Корпус: `tasks/<TASK>/{TASK,CONTEXT,RUBRICS}.md` — из `platformv-arch-bench`
без правок. Контур: `contour/<TASK>/{ACCEPTANCE.md,DEFECTS.yaml,
handoff_quiz.yaml,CONSTRAINTS.contour.yaml}` — генерируется
`runners/contour_prep.py` из файлов авторов.

## Результаты

_Прогон выполняется; таблицы заполняются после его завершения. Никакие числа
здесь не публикуются до прогона — предрегистрация именно в этом и смысл._

## Ограничения

- First-party (см. выше) — главное ограничение, не сноска.
- Совместимость с `platformv-arch-bench` частичная: корпус тот же, протокол
  шире, баллы судьи сравнимы как ориентир, а не как одно измерение.
- Детектор дефектов односторонне смещён: перефразированный, но оставшийся
  ложный тезис может не распознаться → зачёт контура занижается, не
  завышается.
- Стадия 2 идёт на четырёх руках из восьми (стоимость).
- Contamination-контроль не проводился: корпус публиковался ранее.
