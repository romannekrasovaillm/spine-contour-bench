# ACCEPTANCE.md — планка приёмки задачи RDS-LOCK-001

Файл **только для чтения**: он заморожен до прогона (sha256 в
`prereg.lock.json`) и одинаков для всех рук. Собран из файлов авторов
задачи, а не написан составителем бенчмарка:

- требования — CONTEXT.md §2.3–2.5 (таблицы `INF-xx`/`NFR-xx`/`SEC-xx`);
- артефакты — TASK.md §3;
- hard-fail — RUBRICS.md §2;
- лимит объёма — TASK.md frontmatter.

## 1. Требования, подлежащие трассировке

Всего **24** требований (INF-8, NFR-10, SEC-6).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~30 км, каналы 2×10 Гбит/с, RTT 2–4 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Под контуры Radish можно выделить до 6 серверов в каждом ЦОД (x86-64, 8 vCPU, 128 ГБ RAM, NVMe 500 ГБ, ОС Platform V SberLinux OS Server 8.8+) плюс лёгкие ВМ облачной зоны из INF-01 |
| INF-03 | Система записи — кластер АБС-БД (Pangolin) в двух ЦОД; её редизайн вне рамок задачи; Radish — кэш/координационный контур рядом с ней |
| INF-04 | Хранилище секретов банка — HashiCorp Vault (3 узла между ЦОД); допустим SecMan 1.13.0+; секреты в конфигурационных файлах запрещены |
| INF-05 | Мониторинг — Zabbix + Prometheus; аудит — централизованный SIEM |
| INF-06 | Kubernetes-кластеры приложения в обоих ЦОД; сетевые политики: поды не имеют доступа к АБС-БД в обход сервиса справочников |
| INF-07 | Команда: 2 инженера платформы данных (опыт Redis средний, Radish — базовый), 1 администратор ИБ; развёртывание — только Ansible из корпоративного репозитория |
| INF-08 | Политика виртуализации банка: все сервисы на ВМ стартуют под systemd с автоматическим перезапуском (`Restart=always`); отключение автоперезапуска для отдельных сервисов — только по заявке с обоснованием (согласование 2 недели) |
| NFR-01 | Доступность чтения справочников (сервис → кэш) в операционное время (07:00–22:00 МСК) — ≥ 99,95 % в год |
| NFR-02 | Латентность чтения из кэша (p99, на стороне Radish) — ≤ 2 мс при пике 120 000 RPS |
| NFR-03 | Полный прогрев кэша после потери всех данных (из системы записи) — ≤ 30 мин без деградации АБС-БД более 20 % по p99 её OLTP |
| NFR-04 | Устаревание данных в кэше (staleness): курсы валют/котировки — ≤ 60 с |
| NFR-05 | Устаревание прочих справочников (тарифы, параметрика, подразделения) — ≤ 5 мин |
| NFR-06 | Взаимное исключение регламентных операций класса P0 — двойное выполнение недопустимо, в т.ч. при сбоях и переключениях |
| NFR-07 | Захват блокировки (p99) в штатном режиме — ≤ 500 мс |
| NFR-08 | Восстановление контура блокировок после полной потери ЦОД-1 — ≤ 10 мин |
| NFR-09 | Ёмкость кэша — данные 24 ГБ с ростом 20 %/год, горизонт 2 года + 30 % запас |
| NFR-10 | Плановые обновления Radish — без полной недоступности чтения справочников; окно — ночь, будни |
| SEC-01 | TLS для всех соединений: приложение ↔ Radish, репликация, Sentinel-трафик |
| SEC-02 | Аутентификация всех клиентов; раздельные УЗ для кэш-контура и lock-контура; минимальные права (прикладная УЗ кэша не должна иметь доступа к lock-ключам и наоборот) |
| SEC-03 | Секреты (пароли УЗ, `requirepass`/`primaryauth`, ключи TLS) — только из Vault/SecMan, не в конфигурационных файлах |
| SEC-04 | Аудит административных операций (изменения ACL, конфигурации) с выгрузкой в SIEM; маскирование паролей в журналах |
| SEC-05 | Запрет постоянного использования `MONITOR` и команд чтения всего пространства ключей (`KEYS *`) в промышленной среде; диагностика — кратковременно, по заявке |
| SEC-06 | Сетевое разделение: порты Radish (6379), Sentinel (26379) и кластерной шины доступны только из утверждённых сегментов |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | Заявлено, что `WAIT`, `min-replicas-to-write`, durability-режим или Sentinel **гарантируют** отсутствие потерь подтверждённых записей и/или строгую (сильную) консистентность — вопреки прямым оговоркам CONTEXT §1.4/§1.5 |
| HF-02 | Ключи распределённых блокировок размещены на инстансах, где действует политика эвикции `allkeys-lru` (общий инстанс кэша и блокировок), без изоляции контуров — lock-ключ может быть вытеснен |
| HF-03 | Гарантия взаимного исключения P0-операции заявлена на всё время её выполнения (включая случаи длиннее TTL) без механизма fencing/продления и без разбора сценария истечения TTL при живом держателе (нарушение NFR-06 по существу) |
| HF-04 | Вымышленные компоненты или функции Radish поданы как факт (например, «встроенные fencing-токены Radish», «Radish Cluster Manager», «Radish CDC», «keyspace-уведомления как документированная функция», «синхронная репликация Radish между ЦОД») |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
| HF-06 | Для контура(ов) с отключённым persistence штатный автоперезапуск сервисов (INF-08) оставлен без обработки: не отключён автоперезапуск (через заявку по INF-08) и не включён persistence — сценарий «пустой мастер затирает реплики» (CONTEXT §1.6) не закрыт |
