# ACCEPTANCE.md — планка приёмки задачи SGX-ARCH-001

Файл **только для чтения**: он заморожен до прогона (sha256 в
`prereg.lock.json`) и одинаков для всех рук. Собран из файлов авторов
задачи, а не написан составителем бенчмарка:

- требования — CONTEXT.md §2.3–2.5 (таблицы `INF-xx`/`NFR-xx`/`SEC-xx`);
- артефакты — TASK.md §3;
- hard-fail — RUBRICS.md §2;
- лимит объёма — TASK.md frontmatter.

## 1. Требования, подлежащие трассировке

Всего **30** требований (INF-10, NFR-10, SEC-10).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД с DMZ; внешняя балансировка — только существующий GSLB (DNS) и L4-балансировщики DMZ; новых сетевых механизмов (anycast, stretched L2) не вводить |
| INF-02 | Виртуальные машины: 8 vCPU / 16 ГБ RAM / 100 ГБ диск, ОС **SberLinux OS Server 8.10**; под edge-контур выделяется до **3 ВМ на ЦОД**; правило банка: один СПО на ВМ |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, внутренний контур); доступ из DMZ — через межсетевой экран по заявке; SecMan в банке не используется |
| INF-04 | Мониторинг банка — **Prometheus + Grafana** (pull-модель); журналирование — централизованный **SIEM**, приём по syslog; шина Kafka есть, но форвардинг в неё выполняют внешние агенты (RSYSLOG/fluentbit) |
| INF-05 | Перед DMZ уже работает **существующий WAF-контур** банка (отдельное решение); функции WAF от SynGX не требуются и не должны дублироваться |
| INF-06 | Авторизационный сервер банка** (OAuth2/OIDC, выдача JWT access token партнёрам) существует и эксплуатируется отдельной командой; его доработка вне scope задачи |
| INF-07 | Клиентские сертификаты партнёров выдаёт **УЦ банка**; реестр допущенных CN/SAN ведёт ИБ (поставляется в конфигурацию через корпоративный GitOps) |
| INF-08 | Все изменения конфигурации — только через корпоративный GitOps-репозиторий (Ansible) с code review; ручной доступ к ВМ DMZ — через PAM |
| INF-09 | Окно плановых работ в DMZ: ночь 02:00–04:00 МСК, не чаще раза в месяц |
| INF-10 | Команда сопровождения edge-контура: 2 инженера DMZ/сети, 1 инженер ИБ, 1 DevOps; компетенции по Nginx — средние, по SynGX — отсутствуют |
| NFR-01 | Доступность партнёрского API в операционное время (05:00–01:00 МСК) — ≥ 99,95 % в год |
| NFR-02 | Полная потеря ЦОД: переключение трафика партнёров на второй ЦОД — автоматически через GSLB, RTO ≤ 15 мин |
| NFR-03 | Пиковая нагрузка на edge-контур — 6 000 RPS суммарно + 30 % запас; добавочная латентность прокси p99 ≤ 20 мс |
| NFR-04 | Лимиты по тарифам партнёра: «Старт» 50 r/s, «Стандарт» 300 r/s, «Премиум» 1 000 r/s — превышение → отказ с кодом 429; для новых партнёров первый месяц — режим «только наблюдение» (dry-run) |
| NFR-05 | Защита backend-узлов от каскадного отказа при деградации группы (часть узлов выведена healthcheck) — лимит нагрузки на каждый узел группы |
| NFR-06 | Изменение лимита конкретного партнёра (например, временное повышение на маркетинговую кампанию) — без перезагрузки и разрыва соединений, ≤ 5 мин, с автоматическим возвратом к исходному значению |
| NFR-07 | Плановые изменения конфигурации edge-контура — без разрыва установленных соединений клиентов |
| NFR-08 | Наблюдаемость по каждому партнёру: RPS, коды ответов, срабатывания лимитов — задержка данных ≤ 1 мин, выгрузка в Prometheus/Grafana банка |
| NFR-09 | Доставка access-логов и событий аудита в SIEM — ≤ 5 мин |
| NFR-10 | Масштабирование под рост +30 %/год — горизонтально, без перепроектирования схемы |
| SEC-01 | TLS для всех соединений: партнёр ↔ edge, edge ↔ backend, edge ↔ Vault; версии протокола не ниже 1.2, для внешнего контура предпочтительно 1.3 |
| SEC-02 | Аутентификация партнёров на edge по **mTLS**: проверка CN/SAN клиентского сертификата из УЦ банка по реестру ИБ |
| SEC-03 | Проверка OAuth2 access token (JWT) на edge **до** проксирования к backend: подпись, срок действия, scope; выдача токенов — внешний авторизационный сервер (INF-06) |
| SEC-04 | Закрытые TLS-ключи edge-контура **не должны храниться файлами на ВМ в DMZ**; источник сертификатов — Vault банка (INF-03) |
| SEC-05 | Аудит событий идентификации/авторизации и изменений конфигурации; выгрузка в SIEM |
| SEC-06 | Служебные эндпоинты (метрики, управление лимитами, ИИ-агент) — только из внутреннего контура банка / loopback, с TLS и ограничением по адресам |
| SEC-07 | Ротация TLS-сертификатов автоматически, без остановки обслуживания; контроль сроков действия с оповещением |
| SEC-08 | В ответах наружу не раскрываются технические детали (имя и версия прокси-сервера, внутренние имена backend-узлов) |
| SEC-09 | Запрет debug-уровня журналирования в промышленном контуре |
| SEC-10 | Весь административный доступ к ВМ — персонализированный, через PAM (INF-08) |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 2. Обязательные артефакты

| ID | Артефакт |
|---|---|
| D1 | Резюме решения для руководства (≤ 15 строк) |
| D2 | Схема развёртывания (текстовая: Mermaid или PlantUML): узлы SynGX в DMZ двух ЦОД, внешняя балансировка, upstream-сервисы банка, Vault, мониторинг/SIEM |
| D3 | Модель маршрутизации и отказоустойчивости: алгоритмы балансировки, активные healthcheck, поведение при отказе узла/группы/ЦОД, применимость (или обоснованный отказ) sticky-сессий |
| D4 | Контур безопасности: TLS/mTLS, проверка OAuth2 JWT на edge, ACL, интеграция с Vault, аудит, защита служебных эндпоинтов |
| D5 | Модель лимитов и квот партнёров: зоны и ключи лимитирования, пер-узловое лимитирование, мониторинг лимитов, горячее изменение; сопоставление тарифам из CONTEXT.md |
| D6 | Каталог API и жизненный цикл API: границы SynGX, внешние компоненты (каталог/портал как отдельные системы), процесс подключения нового партнёра |
| D7 | Монетизация лимитов: источник данных для тарификации, учёт потребления и превышений по партнёрам, граница с биллингом |
| D8 | Модель эксплуатации: мониторинг (модель сбора метрик), логи и аудит в SIEM, ротация сертификатов, изменение конфигурации, обновления |
| D9 | Таблица трассировки требований → решения |
| D10 | Реестр допущений, рисков, открытых вопросов и отвергнутых альтернатив |

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | SynGX представлен как API-шлюз/API-management: ему как **встроенные факты продукта** приписаны функции, которых нет в документации, — портал разработчика, каталог API, авторизационный сервер OAuth2 (выдача токенов), WAF, биллинг |
| HF-02 | Заявлено, что SynGX **сам** отправляет метрики во внешние системы (push) или пишет логи напрямую в Kafka «из коробки» |
| HF-03 | HA решён «встроенной кластеризацией SynGX» (межинстансовый VRRP/keepalived/синхронизация состояния как функция продукта) без явной пометки, что это внешнее решение; либо топология с единственной точкой отказа на уровне edge при NFR-01 |
| HF-04 | Закрытые TLS-ключи edge-контура хранятся файлами на ВМ в DMZ при наличии документированного потока Vault (ключи только в shared memory) — без явного обоснования отказа и компенсирующих мер (нарушение SEC-04) |
| HF-05 | Эндпоинт горячего управления лимитами (`limit_req_change`) выставлен за пределы loopback/unix-сокета (нарушение документированного ограничения и SEC-06) |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 |

- Язык: русский; англоязычные технические термины допустимы.
