Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | Заключение **декларирует соответствие** ландшафта требованиям как факт («ландшафт соответствует 719-П», «продукты обеспечивают соответствие») вместо фиксации механизмов и остаточных мер — нарушение правила карты (CONTEXT §1.1) |
| HF-02 | 683-П применён как **действующий** акт: нормы 683-П использованы в матрице без пометки об утрате силы и замене на 851-П (CONTEXT §1.10–1.11) |
| HF-03 | Вымышленные/искажённые функции продуктов поданы как факт: TDE в редакции Standard; Radish как MPP/OLAP или система записи критичных данных; DataMarts как OLTP/система записи; WAF в составе SynGX; штатный прямой CDC в DataMarts; «Records Policy — функция Apache Kafka» |
| HF-04 | Процессы, которые продукт по определению не выполняет (ежегодный pentest, оценка соответствия по 57580.2, сертификация ПО, классификация данных, DR-учения), приписаны продуктам Platform V как штатная функция |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
