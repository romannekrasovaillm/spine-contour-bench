## 1. Требования, подлежащие трассировке

Всего **28** требований (INF-8, NFR-12, SEC-8).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), ~40 км, выделенные каналы 2×10 Гбит/с, RTT 2–4 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64, ОС **Platform V SberLinux OS Server 10**; в каждом ЦОД под целевой контур СУБД можно выделить до 4 серверов (2×32 ядра, 512 ГБ RAM, NVMe **16 ТБ**) |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, растянут между ЦОД, RTO ≤ 5 мин). Эмуляторы KMS в промышленной среде запрещены политикой ИБ |
| INF-04 | СРК банка предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; интеграция — через штатные средства СУБД |
| INF-05 | Мониторинг — **Zabbix**; журналирование — централизованный SIEM; административный доступ — только через **PAM**; развёртывание — только Ansible из корпоративного репозитория |
| INF-06 | Под миграционный стенд выделяется отдельное оборудование ЦОД-1 (до 3 серверов той же конфигурации); тестовые данные с ПДн — только обфусцированные |
| INF-07 | Команда проекта: 5 DBA (Oracle — глубоко, PostgreSQL — средне, Pangolin — базово), 2 DevOps, 1 администратор ИБ; внешняя интеграторская поддержка не планируется |
| INF-08 | Окно планового простоя: 1 раз в квартал, ночь с субботы на воскресенье, **не более 4 часов**; бизнес допускает прерывание **записи** при cutover не более 15 минут (приём операций ставится в очередь интеграционного слоя) |
| NFR-01 | Доступность АС РГА (24/7) в период миграции и после — ≥ 99,95 % в год |
| NFR-02 | RPO целевого контура при отказе узла внутри ЦОД — 0 |
| NFR-03 | RTO целевого контура при отказе узла (автоматическое переключение) — ≤ 3 мин |
| NFR-04 | RPO при полной потере ЦОД-1 — ≤ 60 с |
| NFR-05 | RTO при полной потере ЦОД-1 (допускается ручное решение) — ≤ 60 мин |
| NFR-06 | Латентность OLTP-транзакции (p99) на стороне СУБД — ≤ 20 мс при 8 500 TPS |
| NFR-07 | Непрерывность миграции**: остановки приёма операций нет; прерывание записи на cutover — ≤ 15 мин (INF-08) |
| NFR-08 | Полнота переноса**: расхождения данных Oracle ↔ Pangolin на момент cutover — 0 по бизнес-ключам и контрольным суммам |
| NFR-09 | Обратимость**: окно отката на Oracle после cutover без потери операций, принятых в Pangolin; время возврата — окно ≥ 30 дней; возврат ≤ 60 мин |
| NFR-10 | Ночной пакет загрузки реестров на целевом контуре — ≤ 3 ч, без блокировки OLTP |
| NFR-11 | Ёмкость целевого контура — 7 лет хранения при росте 1,8 ТБ/год + 30 % запас |
| NFR-12 | PITR на целевом контуре — глубина 35 дней; восстановление полной БД ≤ 8 ч |
| SEC-01 | Данные АС РГА (ПДн + банковская тайна) шифруются «на диске» на целевом контуре; ключи — во внешнем хранилище секретов банка (INF-03). TDE целевого контура включается **до начала** перелива продуктивных данных |
| SEC-02 | Ни один администратор (DBA, ОС, ИБ, РК) в одиночку не должен иметь возможность прочитать содержимое защищаемых таблиц |
| SEC-03 | Разделение обязанностей: включение TDE, изменение состава расширений, выдача доступа к защищаемым объектам — с участием администратора ИБ |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной и миграционный доступ — ТУЗ с минимальными правами |
| SEC-05 | Аудит событий безопасности по ГОСТ Р 59548-2022 с выгрузкой в SIEM; маскирование параметров запросов в журналах |
| SEC-06 | TLS для всех соединений миграционного и целевого контуров (клиенты, репликация, CDC-канал, FDW-мосты); сертификаты из корпоративного УЦ |
| SEC-07 | Данные в миграционном контуре (стенды, промежуточные выгрузки, CDC-трафик) защищены не слабее продуктивных; тестовые стенды — только с обфусцированными данными (INF-06) |
| SEC-08 | Используемая редакция Pangolin должна покрывать все задействованные функции; выбор редакции обосновать |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | `pgloader` предложен как инструмент миграции **с Oracle** (схема или данные), подано как факт/решение. В документации источники pgloader — только MS SQL Server / MySQL / SQLite |
| HF-02 | `pgcopydb` предложен как канал миграции/CDC **с источника Oracle**, либо `pgcopydb follow` — при включённом TDE на приёмнике без явной оговорки о документированной несовместимости — подано как рабочее решение |
| HF-03 | Вымышленные компоненты/функции поданы как факт: «Pangolin нативно исполняет PL/SQL», «встроенный CDC-коннектор Oracle → Pangolin в составе Pangolin», «wal2json читает журналы Oracle», «Pangolin GoldenGate», вымышленные пакеты/утилиты |
| HF-04 | Стратегия «big bang»: полная перекладка 12 ТБ в квартальное окно 4 часа (или аналогичное) **без** предварительной загрузки и CDC-досинхронизации — при действующем NFR-07 |
| HF-05 | Заявлен RPO = 0 на DR-контуре (между ЦОД) или на CDC-канале при асинхронной репликации без оговорок; либо предложен **автоматический** promote standby-кластера при двух ЦОД без разбора документированного ограничения (DC2 не отличает сбой DC1 от разделения; promote — ручной, со STONITH) |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
