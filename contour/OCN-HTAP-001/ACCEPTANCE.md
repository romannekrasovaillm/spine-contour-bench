## 1. Требования, подлежащие трассировке

Всего **28** требований (INF-9, NFR-11, SEC-8).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~35 км, выделенные каналы 2×10 Гбит/с, RTT между ЦОД 2–3 мс. Третьей площадки **нет**; есть возможность разместить до 2 **лёгких ВМ (4 vCPU / 8 ГБ)** в «облачной зоне» банка, сетево независимой от обоих ЦОД. Выделение полноценного сервера вне двух ЦОД — изменение ограничения, требует отдельного решения ИТ-инфраструктуры (срок 3–4 месяца) |
| INF-02 | Серверы x86-64: до **6 серверов в каждом ЦОД** под СУБД-слой (2×32 ядра, 512 ГБ RAM, NVMe 6×3,84 ТБ ≈ 23 ТБ на сервер) |
| INF-03 | Стандарт ОС банка — **Platform V SberLinux OS Server** (эксплуатируются ветки 9.x и 10.x; выбор редакции согласуется с ОТБ) |
| INF-04 | Хранилище секретов — HashiCorp Vault (3 узла, растянут между ЦОД), латентность из обоих ЦОД ≤ 5 мс |
| INF-05 | СРК предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; требуется интеграция штатными средствами СУБД |
| INF-06 | Мониторинг Zabbix обязателен для промышленных систем; Prometheus/Grafana допустимы как дополнительный контур; аудит — в SIEM |
| INF-07 | Kubernetes-кластеры приложения (Platform V DropApp) в обоих ЦОД, приложение active-active; балансировщики L4/L7 банка доступны в обоих ЦОД |
| INF-08 | Команда сопровождения: 4 DBA (PostgreSQL/Pangolin — уверенно, MySQL — базово, Ocean DB — **нет опыта**), 1 администратор ИБ, 2 DevOps; контракт поддержки вендора 24×7 доступен |
| INF-09 | Окно плановых работ: ночь, не более 2 часов, не чаще раза в квартал; **приём авторизаций при этом не прерывается |
| NFR-01 | Доступность АС АФ-КО (круглосуточно, 7×24×365) — ≥ 99,95 % в год |
| NFR-02 | Латентность записи авторизации на стороне СУБД (p99) при пике 4 200 TPS — ≤ 10 мс |
| NFR-03 | Отказ одного узла или одной зоны доступности — RPO = 0**; RTO ≤ 60 с, автоматически |
| NFR-04 | Полная потеря ЦОД-1 — RPO = 0**; RTO ≤ 15 мин (допускается ручное решение о переключении) |
| NFR-05 | Оперативная аналитика антифрода по свежим данным (лаг ≤ 60 с) — без деградации OLTP более чем на 5 % по p99 |
| NFR-06 | Синхронные онлайн-проверки в пути авторизации (точечные lookups) — СУБД-бюджет p99 ≤ 5 мс |
| NFR-07 | Сезонный пик ≈ 10 500 TPS до 7 дней — без изменения аппаратного состава; допустимая деградация p99 ≤ 25 мс |
| NFR-08 | Ёмкость — 3 года онлайн + 30 % запас |
| NFR-09 | Восстановление на момент времени (PITR) — глубина 30 дней; RTO восстановления полной БД из копии ≤ 6 ч |
| NFR-10 | Плановые обновления СУБД и плановые работы — без прерывания приёма авторизаций |
| NFR-11 | Одновременные подключения от приложения — до 3 000 |
| SEC-01 | Данные авторизаций (банковская тайна, PCI DSS) шифруются «на диске»; ключи — во внешнем хранилище секретов банка (Vault). Документированный статус шифрования хранимых данных у Ocean DB — см. §1.11 п. 3 |
| SEC-02 | TLS 1.2+ для всех соединений (клиент ↔ OBPROXY ↔ узлы, межузловые); сертификаты корпоративного УЦ, ротация без простоя |
| SEC-03 | Разделение обязанностей: ни один администратор (DBA, ОС, ИБ) в одиночку не должен иметь возможность читать содержимое защищаемых таблиц |

| SEC-05 | Аудит DDL и операций с защищаемыми объектами с передачей в SIEM |
| SEC-06 | АС АФ-КО в периметре КИИ/ГОП: предпочтительно ПО с сертификацией ФСТЭК; при её отсутствии — явное риск-решение с компенсирующими мерами |
| SEC-07 | PCI DSS: сегментация CDE, минимизация хранения PAN (маскирование/токенизация на уровне приложения — вне скоупа СУБД, но должно быть учтено) |
| SEC-08 | Резервные копии не должны позволять восстановить открытые данные без ключей из хранилища секретов |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 2. Обязательные артефакты

| ID | Артефакт |
|---|---|
| D1 | Резюме решения для руководства (≤ 15 строк) |
| D2 | Схема развёртывания (текстовая: Mermaid или PlantUML): узлы и зоны OBSERVER, OBPROXY-ферма за балансировщиком, OBAGENT, арендаторы, оба ЦОД, СРК, мониторинг |
| D3 | Конфигурация RPO = 0 и HA/DR: раскладка зон доступности и Paxos-групп, сценарии отказа узла/зоны/ЦОД-1, проектное значение RTO с разбором расхождения вендора, роль OBPROXY при перевыборах лидеров партиций |
| D4 | Модель HTAP и изоляция нагрузок: распределение нагрузок антифрода по механизмам продукта (реплики-подписчики, арендаторы, Resource Units с расчётом квот), решение по размещению аналитики относительно арендаторов, границы HTAP (что выносится из контура и почему) |
| D5 | Производительность и ёмкость: сопоставление с НФТ вендора (§1.6 CONTEXT.md) с оговорками, расчёт ёмкости 3 года + 30 % с учётом сжатия и фактора репликации, вывод по достаточности INF-02, расчёт подключений |
| D6 | Подключение приложения и совместимость: OBPROXY (порты, формат пользователя, stateless-масштабирование), драйверы OBCLIENT/JDBC, статус совместимости MySQL-диалекта, план проверки |
| D7 | Эксплуатация и резервное копирование: обязательная ОС и согласование со стандартом банка, установка (RLM), обновления без прерывания приёма (NFR-10), мониторинг (OBAGENT, Prometheus/Grafana, Zabbix), архивирование на NFS/S3 и PITR (NFR-09) |
| D8 | Безопасность и соответствие: покрытие SEC-01…SEC-08 документированными средствами; явный реестр пробелов (§1.11 CONTEXT.md) с вопросами к вендору и компенсирующими мерами |
| D9 | Таблица трассировки требований → решения |
| D10 | Реестр допущений, рисков, открытых вопросов и отвергнутых альтернатив |

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | Конфигурация заявлена как выполняющая NFR-04 (**RPO = 0 и RTO ≤ 15 мин при полной потере ЦОД-1**), хотя большинство реплик Paxos-групп размещено в ЦОД-1 (например, раскладка зон 2+1 или 2 зоны всего) — и это противоречие не признано / не компенсировано (третья зона, изменение INF-01, явное отклонение требования). Коммит подтверждается большинством: потеря большинства = недоступность без перевыборов |
| HF-02 | Недокументированные возможности (CONTEXT §1.11) поданы как **факт**: Oracle-режим арендаторов, штатный CDC/интеграция с Kafka, шифрование хранимых данных (TDE-эквивалент) у Ocean DB, сертификация ФСТЭК/поддержка ГОСТ у Ocean DB, межкластерная standby-репликация, арбитражная реплика зоны |
| HF-03 | RTO < 8 с (или ≤ 10 с) заявлен как **гарантированный** НФТ решения без оговорки о расхождении вендора (сводная страница «Преимущества» заявляет < 30 с, в ADR закладывать 30 с) |
| HF-04 | Эксплуатация Ocean DB на ОС, отличной от SberLinux OS Server **9.6.2** (например, «на SberLinux 10.2.1 как стандарте банка» или Astra Linux), принята как допустимая без вопроса к вендору |
| HF-05 | Транзакционная и аналитическая нагрузки размещены совместно **без какой-либо изоляции**: ни квот Resource Unit, ни направления аналитики на реплики-подписчики (повторение проблемы AS-IS при NFR-05) |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
