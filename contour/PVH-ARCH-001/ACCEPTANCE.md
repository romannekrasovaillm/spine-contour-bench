| NFR-04 | Первичная загрузка ~100 000 объектов CMDB при миграции — ≤ 8 ч, без блокировки интерактивной работы в дневное время (выполняется в выходные) |
| NFR-05 | Формирование надзорной выгрузки (все АС + владельцы + критичность) — ≤ 10 мин, без участия ИТ (self-service для уполномоченного сотрудника ДКА) |
| NFR-06 | Полная историчность изменений объектов (кто/когда/что изменил) — 100 % операций изменения; хранение истории ≥ 5 лет |
| NFR-07 | RPO приложения-реестра — ≤ 15 мин; RTO ≤ 4 ч (восстановление во втором ЦОД) |
| NFR-08 | Масштабирование модели данных: добавление нового типа ОУ или атрибута — без перепроектирования БД вручную; через релиз приложения ≤ 1 релизный цикл (2 недели) |
| NFR-09 | Рост объёма данных +20 % в год — без смены архитектуры в горизонте 5 лет (до ~300 тыс. объектов) |
| NFR-10 | Актуальность технологических атрибутов АС (стек, версии фреймворков) по данным репозиториев — отставание от репозитория ≤ 24 ч |
| SEC-01 | Аутентификация всех пользователей — только через корпоративный IAM (Keycloak SE, INF-03); локальных учётных записей нет |
| SEC-02 | Ролевая модель минимум из ролей: «читатель», «архитектор домена» (редактирование своего домена), «администратор реестра» (управление типами, статусами, справочниками), «аудитор» (чтение всего + история); доменный архитектор не должен редактировать чужие домены |
| SEC-03 | Все операции изменения данных — с персональной атрибуцией и аудитом; события аудита выгружаются в SIEM (INF-09) |
| SEC-04 | TLS ≥ 1.2 на всех стыках: пользователь ↔ SynGX, SynGX ↔ приложение, приложение ↔ БД/брокер/IAM/CMDB |
| SEC-05 | Секреты интеграций (токены CMDB API, ключи брокера, credentials БД) — только в корпоративном Vault; в коде и конфигурационных файлах GitVerse секретов быть не должно |
| SEC-06 | Разделение контуров test/prom; в test — только обфусцированные данные (владельцы АС — персональные данные: ФИО, табельные номера) |
| SEC-07 | Доступ администраторов к инфраструктуре — через PAM; прямой доступ к БД — только учётной записи приложения и штатной ТУЗ мониторинга (INF-02) |
| SEC-08 | В атрибутах реестра минимизируются ПДн: ФИО владельцев хранятся как ссылки на штатное расписание (ID сотрудника), отображение по требованию |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | Architect Hub представлен как готовый EA-репозиторий «из коробки»: ему как **встроенные факты продукта** приписаны готовый UI/портал для архитекторов, дашборды, штатный импорт из Excel/Confluence/ArchiMate или предконфигурированная метамодель/набор реестров |
| HF-02 | Продукту приписаны функции визуального моделирования (диаграммы, нотации C4/ArchiMate, viewpoints, графическая коллаборация) как факт |
| HF-03 | Вымышленные компоненты, Maven-артефакты или классы BECF поданы как факт (например, «Architect Hub Server», `met-configurator-ui`, `met-import-tool`, «консоль администратора Architect Hub») |
| HF-04 | Решение обещает внедрение реестра «настройкой/конфигурированием без разработки»: типы ОУ, операции, права или DDL предлагается ввести без Java-кода, компиляции и релиза приложения — вопреки документированной модели SDK |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
