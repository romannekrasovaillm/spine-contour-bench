## 1. Требования, подлежащие трассировке

Всего **30** требований (INF-8, NFR-12, SEC-10).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~45 км, выделенные каналы 2×10 Гбит/с, RTT между ЦОД 2–3 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64, ОС **Platform V SberLinux OS Server**; в каждом ЦОД можно выделить до 4 серверов под СУБД (2×32 ядра, 512 ГБ RAM, NVMe 8 ТБ) |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, растянут между ЦОД). KMS-заменитель Pangolin использовать в промышленной среде **запрещено** политикой ИБ |
| INF-04 | Система резервного копирования (СРК) банка предоставляет S3-совместимое и NFS-хранилище в каждом ЦОД; требуется интеграция через штатные средства СУБД |
| INF-05 | Мониторинг — **Zabbix**; журналирование — централизованный SIEM; управление привилегированным доступом — **PAM-система** (все административные сессии только через PAM) |
| INF-06 | Kubernetes-кластеры приложения есть в обоих ЦОД (active/standby по приложению) |
| INF-07 | Команда сопровождения: 4 DBA (опыт PostgreSQL средний, Pangolin — базовый), 1 администратор ИБ, 2 DevOps; развёртывание — только Ansible из корпоративного репозитория |
| INF-08 | Окно планового простоя: 1 раз в квартал, ночь с субботы на воскресенье, **не более 4 часов |
| NFR-01 | Доступность в операционное время (05:00–23:00 МСК) — ≥ 99,95 % в год |
| NFR-02 | RPO при отказе узла / стойки внутри ЦОД — 0** (подтверждённые транзакции не теряются) |
| NFR-03 | RTO при отказе узла внутри ЦОД (автоматическое переключение) — ≤ 3 мин |
| NFR-04 | RPO при полной потере ЦОД-1 — ≤ 60 с |
| NFR-05 | RTO при полной потере ЦОД-1 (допускается ручное решение о переключении) — ≤ 30 мин |
| NFR-06 | Латентность OLTP-транзакции (p99) на стороне СУБД — ≤ 15 мс при 12 000 TPS |
| NFR-07 | Аналитические запросы не должны деградировать OLTP более чем на 5 % по p99 — — |
| NFR-08 | Ночной пакет 25 млн строк — ≤ 2 ч, без блокировки OLTP |
| NFR-09 | Ёмкость — 5 лет хранения при росте 1,2 ТБ/год + 30 % запас |
| NFR-10 | Восстановление на момент времени (PITR) — глубина 35 дней; RTO восстановления полной БД из копии ≤ 6 ч |
| NFR-11 | Плановые обновления минорных версий СУБД и компонентов — без простоя приложения |
| NFR-12 | Мажорные обновления — в окне INF-08 |
| SEC-01 | Данные платёжных поручений (ПДн + банковская тайна) шифруются «на диске»; ключи — во внешнем хранилище секретов банка |
| SEC-02 | Ни один администратор (DBA, ОС, ИБ, РК) в одиночку не должен иметь возможность прочитать содержимое защищаемых таблиц |
| SEC-03 | Разделение обязанностей: включение TDE, изменение состава расширений, настройка сетевой защиты и выдача доступа к защищаемым объектам требуют участия администратора ИБ |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной доступ — только через ТУЗ с минимальными правами |
| SEC-05 | Аудит DDL и всех операций с защищаемыми объектами; передача в SIEM; маскирование параметров запросов в журналах |
| SEC-06 | TLS для всех соединений (клиент ↔ пул ↔ СУБД, узлы кластера ↔ DCS, REST API оркестратора); сертификаты из корпоративного УЦ, ротация не реже раза в год без простоя |
| SEC-07 | Парольные политики для локальных УЗ (сложность, срок действия, история) |
| SEC-08 | Резервные копии не должны позволять восстановить открытые данные без ключей из хранилища секретов |
| SEC-09 | Для DBA — двухфакторная аутентификация |
| SEC-10 | Использовать сертифицированную ФСТЭК редакцию либо обосновать применение несертифицированной с компенсирующими мерами |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | DCS без кворума: предложено 1 узел или чётное число узлов DCS **без** явного обоснования и компенсирующих мер (например, осознанный отказ от автоматического failover при потере ЦОД) |
| HF-02 | Заявлено, что TDE **сама по себе** защищает данные от суперпользователя СУБД или администратора ОС (без механизма защиты от привилегированных пользователей и администратора безопасности) |
| HF-03 | Вымышленные компоненты или функции Pangolin поданы как факт (например, «Pangolin Proxy», «встроенный балансировщик Pangolin», «нативная поддержка PL/SQL», «Pangolin Vault») |
| HF-04 | Заявлен RPO = 0 при потере ЦОД-1 при асинхронной репликации в ЦОД-2, либо RPO = 0 без указания режима репликации вообще |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
