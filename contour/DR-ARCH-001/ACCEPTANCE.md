## 1. Требования, подлежащие трассировке

Всего **24** требований (INF-8, NFR-10, SEC-6).

| ID | Требование |
|---|---|
| INF-01 | Ровно два ЦОД; внешняя балансировка — только существующий GSLB (DNS) и L4-балансировщики DMZ с VIP; новых сетевых механизмов (anycast, stretched L2, третья площадка для кворумов) не вводить |
| INF-02 | Версии продуктов зафиксированы: Pangolin DB 8.2.0 (редакция Enterprise), Corax 16.392.0, SynGX 4.3.0; обновление версий вне scope задачи |
| INF-03 | ОС всех ВМ — SberLinux OS Server 8.10; ВМ по шаблону 8 vCPU / 32 ГБ RAM (брокеры и узлы БД), 8 vCPU / 16 ГБ RAM (SynGX) |
| INF-04 | Хранилище секретов — кластер HashiCorp Vault (внутренний контур, развёрнут в обоих ЦОД); SecMan в банке не используется; сертификаты Corax выпускаются корпоративным УЦ и раскатываются Ansible |
| INF-05 | Мониторинг банка — Prometheus + Grafana (pull-модель); журналирование — централизованный SIEM (приём по syslog); Platform V Monitor (COTE) не развёрнут — аудит Corax пишется в лог-файл |
| INF-06 | S3-совместимое хранилище банка (в третьем, отдельном здании) доступно обоим ЦОД по выделенному каналу; используется для бэкапов |
| INF-07 | Все изменения конфигурации — только через корпоративный GitOps (Ansible) с code review; ручной доступ к ВМ — через PAM, персонализированный |
| INF-08 | Команда сопровождения контура: 2 DBA, 2 инженера middleware, 1 сетевой инженер, 1 инженер ИБ + дежурная смена 24×7; решение о переключении ЦОД принимает дежурный руководитель смены по процедуре эскалации; критичные ручные операции (promote) — по правилу «четырёх глаз» |
| NFR-01 | Классы критичности и целевые RTO/RPO: **класс А** — платёжное ядро (БД): RTO ≤ 30 мин, RPO = 0; **класс Б** — шина событий: RTO ≤ 30 мин, RPO ≤ 5 мин; **класс В** — точка входа (edge): RTO ≤ 15 мин, потеря состояния сессий/лимитов допустима, конфигурация RPO = 0 — подтверждать учениями |
| NFR-02 | Сквозная согласованность после DR: ни одна операция, подтверждённая клиенту до отказа, не должна быть потеряна; «зависшие» платежи после переключения должны автоматически выявляться и разбираться по процедуре ≤ 4 ч — обязательно |
| NFR-03 | Доступность платёжного контура в операционное время (04:00–01:00 МСК) — ≥ 99,95 % в год |
| NFR-04 | Обнаружение отказа ЦОД и решение о переключении — детекция ≤ 5 мин; решение по процедуре эскалации ≤ 10 мин после детекции |
| NFR-05 | Отказоустойчивость внутри ЦОД (узел БД, брокер, узел edge) — автоматически, без участия дежурной смены, RTO ≤ 5 мин |
| NFR-06 | Контроль лага репликации между ЦОД (БД и шина) — SLO лага шины ≤ 60 с в штатном режиме; алерт при превышении; фактический RPO шины должен быть измерим в каждый момент |
| NFR-07 | Плановый возврат на основной ЦОД после устранения аварии — без потери данных, в плановое окно, с подтверждением целостности |
| NFR-08 | DR-учения: полномасштабные (переключение контура) — ≥ 2 раз в год; компонентные (отказ узла/брокера) — ежеквартально; проверка процедур «на бумаге» (tabletop) — ежеквартально — фиксация результатов и актуализация плана |
| NFR-09 | Наблюдаемость DR-готовности: в любой момент дежурная смена видит, что резервный ЦОД способен принять контур — дашборд + алерты в Prometheus/Grafana банка |
| NFR-10 | Документация DR-плана актуализируется после каждого учения и каждого инцидента — версии в GitOps, review ДКА |
| SEC-01 | Все межЦОД-каналы репликации (БД, шина) — TLS не ниже 1.2; взаимная аутентификация сертификатами корпоративного УЦ |
| SEC-02 | Закрытые TLS-ключи edge-контура не хранятся файлами на ВМ в DMZ (источник — Vault, INF-04) |
| SEC-03 | Все ручные операции DR (promote, переключение направления репликации, изменение маршрутизации) — персонализированные, через PAM, с журналированием в SIEM |
| SEC-04 | Доступность секретов при DR: потеря одного ЦОД не должна лишить резервный ЦОД доступа к Vault/УЦ (INF-04) |
| SEC-05 | Аудит событий всех трёх продуктов (включая события авторизации Corax и аудит изменений конфигурации SynGX) доставляется в SIEM ≤ 5 мин |
| SEC-06 | Пароли в конфигурациях Corax — только в зашифрованном виде (штатные утилиты шифрования паролей); открытые пароли в GitOps запрещены |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | DR для Pangolin построен на **растянутом синхронном кластере на 2 ЦОД с автоматическим failover** или на **автоматическом promote standby-кластера** — подано как решение, вопреки прямой рекомендации документации (CONTEXT §1.4) |
| HF-02 | Сквозному контуру (БД + шина + шлюз) приписан **RPO = 0** без оговорки об асинхронности межкластерной репликации Corax Mirror Maker 2; либо MM2 заявлен как синхронный механизм |
| HF-03 | Продуктам приписаны **отсутствующие DR-функции**: межинстансовая кластеризация/синхронизация состояния SynGX (VRRP, общие лимиты), автоматическое переключение клиентов шины между кластерами средствами MM2, штатный бэкап Corax в файловое хранилище и т.п. |
| HF-04 | Вывод standby-кластера из-под репликации предложен штатно через **`pg_ctl promote`** (документация: удаление секции `standby_cluster` из динамической конфигурации) и/или процедура promote **без STONITH** основного сайта |
| HF-05 | Платёжные топики спроектированы с `acks=1` / `min.insync.replicas=1` по образцу НФТ-стенда вендора, поданному как рекомендация для прода (CONTEXT §1.7: это параметры производительного теста) |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
