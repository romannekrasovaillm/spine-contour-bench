## 1. Требования, подлежащие трассировке

Всего **25** требований (INF-8, NFR-10, SEC-7).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД (ЦОД-1 «Основной», ЦОД-2 «Резервный»), расстояние ~40 км, выделенные каналы 2×10 Гбит/с, RTT между ЦОД 2–3 мс. Третьей площадки **нет**; есть возможность разместить до 2 лёгких ВМ (4 vCPU / 8 ГБ) в «облачной зоне» банка, сетево независимой от обоих ЦОД |
| INF-02 | Серверы x86-64: до **9 серверов в каждом ЦОД** под СУБД-слой (2×24 ядра, 384 ГБ RAM, NVMe 6×3,84 ТБ) |
| INF-03 | Стандарт ОС банка — **Platform V SberLinux OS Server** (эксплуатируются ветки 9.x и 10.x; выбор редакции согласуется с ОТБ) |
| INF-04 | СРК предоставляет S3-совместимое и NFS-хранилище в **каждом** ЦОД; требуется интеграция штатными средствами СУБД |
| INF-05 | Мониторинг Zabbix обязателен для промышленных систем; Prometheus/Grafana допустимы как дополнительный контур; аудит — в SIEM |
| INF-06 | Kubernetes-кластеры приложения (Platform V DropApp) в обоих ЦОД, приложение active-active; балансировщики L4/L7 банка доступны в обоих ЦОД |
| INF-07 | Команда сопровождения: 5 DBA (PostgreSQL/Pangolin — уверенно, MySQL — базово, Ocean DB — **нет опыта**), 1 администратор ИБ, 2 DevOps; контракт поддержки вендора 24×7 доступен |
| INF-08 | Окна плановых работ: ночь, не более 2 часов, не чаще раза в квартал; **приём авторизаций при этом не прерывается |
| NFR-01 | Доступность АС ФАП (круглосуточно, 7×24×365) — ≥ 99,95 % в год |
| NFR-02 | Латентность транзакции на стороне СУБД (p99) при пике 3000 TPS — ≤ 10 мс |
| NFR-03 | Отказ одного узла или одной зоны доступности — RPO = 0; RTO ≤ 60 с, автоматически |
| NFR-04 | Полная потеря ЦОД-1 — RPO ≤ 5 мин; RTO ≤ 60 мин (допускается ручное решение) |
| NFR-05 | Сезонный пик ≈9000 TPS до 10 дней — без изменения аппаратного состава; допустимая деградация p99 ≤ 25 мс |
| NFR-06 | Ёмкость — 5 лет онлайн при ~50 ТБ/год + 30 % запас |
| NFR-07 | Антифрод/отчётность по свежим данным (лаг ≤ 5 мин) — без деградации OLTP более чем на 5 % по p99 |
| NFR-08 | PITR — глубина 35 дней; RTO восстановления полной БД из копии ≤ 8 ч |
| NFR-09 | Плановые обновления СУБД (минорные и в рамках линейки) — без остановки приёма авторизаций |
| NFR-10 | Одновременные подключения от приложения — до 2 500 |
| SEC-01 | Данные авторизаций (банковская тайна, PCI DSS) шифруются «на диске»; ключи — во внешнем хранилище секретов банка (Vault) |
| SEC-02 | TLS 1.2+ для всех соединений (клиент ↔ прокси ↔ узлы, межузловые); сертификаты корпоративного УЦ, ротация без простоя |
| SEC-03 | Разделение обязанностей: ни один администратор (DBA, ОС, ИБ) в одиночку не должен иметь возможность читать содержимое защищаемых таблиц |
| SEC-04 | Все административные подключения — персонализированные, через PAM; прикладной доступ — только через ТУЗ с минимальными правами |
| SEC-05 | Аудит DDL и операций с защищаемыми объектами с передачей в SIEM |
| SEC-06 | АС ФАП находится в периметре ГОП/КИИ: предпочтительно ПО с сертификацией ФСТЭК; при её отсутствии — явное риск-решение с компенсирующими мерами |
| SEC-07 | Соответствие PCI DSS: сегментация CDE, минимизация хранения PAN (маскирование/токенизация на уровне приложения — вне скоупа СУБД, но должно быть учтено) |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | Топология Ocean DB без кворума: предложено **менее 3 зон/реплик** (или чётный состав Paxos-группы) без явного обоснования и компенсирующих мер; либо **большинство зон размещено в одном ЦОД** и при этом заявлена автоматическая доступность при потере этого ЦОД |
| HF-02 | Вымышленные или переименованные компоненты поданы как факт («Ocean Manager», «Ocean Pooler», «Ocean DCS», «Ocean Vault», «OCP-кластер» и т.п.) вместо официальных OBSERVER / OBAGENT / OBPROXY / OBCLIENT / RootService / Resource Unit |
| HF-03 | Недокументированные возможности Ocean DB 1.1.0 (CONTEXT §1.9) поданы как **факт**: Oracle-режим арендаторов, сертификация ФСТЭК/ФСБ, ГОСТ-криптография, CDC в Kafka, межкластерная/standby-репликация — без пометки «требует проверки у вендора» |
| HF-04 | Заявлен **RPO = 0 при полной потере ЦОД-1** для топологии, где большинство зон (2 из 3) находится в одном ЦОД, без описания механизма сохранения кворума |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
