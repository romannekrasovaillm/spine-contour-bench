Файл **только для чтения**: он заморожен до прогона (sha256 в
`prereg.lock.json`) и одинаков для всех рук. Собран из файлов авторов
задачи, а не написан составителем бенчмарка:

## 1. Требования, подлежащие трассировке

Всего **30** требований (INF-10, NFR-10, SEC-10).

| ID | Требование |
|---|---|
| INF-01 | Два ЦОД; балансировка — только существующие **L4-балансировщики** банка (VIP на сегментный шлюз в каждом ЦОД) и **внутренний DNS** (имена вида `<ac>.int-gw.terracapital.local`); новых сетевых механизмов (anycast, stretched L2, service discovery-платформ) не вводить |
| INF-02 | Виртуальные машины под шлюзы: 8 vCPU / 16 ГБ RAM / 100 ГБ диск, ОС **SberLinux OS Server 8.10**; правило банка — один СПО на ВМ; лимит мощностей: до **2 ВМ SynGX на сегмент на ЦОД**, для двух критичных сегментов (ДБО-ядро, карточный) — до 3 ВМ на ЦОД |
| INF-03 | Хранилище секретов банка — кластер **HashiCorp Vault** (3 узла, внутренний сервисный сегмент, PKI-движок настроен); доступ из сегментов — через МЭ по заявке; SecMan в банке не используется |
| INF-04 | Мониторинг банка — **Prometheus + Grafana** (pull-модель); журналирование — централизованный **SIEM**, приём по syslog; коллектор трассировки **OpenTelemetry** (приём по TLS); шина Kafka есть, но форвардинг в неё выполняют внешние агенты (RSYSLOG/fluentbit) |
| INF-05 | Клиентские сертификаты АС выпускает **УЦ банка**; реестр допущенных CN/SAN (системные идентификаторы АС) ведёт ИБ и поставляет в конфигурацию через корпоративный GitOps; срок действия сертификатов АС — 1 год, цель — 90 дней |
| INF-06 | Все изменения конфигурации — только через корпоративный GitOps-репозиторий (Ansible) с code review; ручной доступ к ВМ — через PAM, персонализированный |
| INF-07 | Из 40 АС контейнеризованы в K8s лишь 6 (пилот); остальные — ВМ и физические серверы. Доработка АС-потребителей ограничена: смена точки вызова на DNS-имя шлюза + предъявление клиентского сертификата АС |
| INF-08 | 5 устаревших АС** казначейства и DWH не могут предъявлять клиентский TLS-сертификат до их модернизации (срок — конец 2027); для них требуются компенсирующие меры на переходный период |
| INF-09 | Окно плановых работ: ночь 02:00–05:00 МСК, не чаще раза в месяц; критичные сегменты (ДБО, карточный) работают 24×7 |
| INF-10 | Команда сопровождения: 2 инженера интеграции, 1 инженер ИБ, 1 DevOps; компетенции по Nginx — средние, по SynGX — отсутствуют |
| NFR-01 | Доступность критичных сегментных шлюзов (ДБО-ядро, карточный) — ≥ 99,95 % в год (24×7) |
| NFR-02 | Полная потеря ЦОД: переключение внутреннего трафика на второй ЦОД — автоматически (DNS/L4), RTO ≤ 15 мин для критичных сегментов |
| NFR-03 | Пиковая нагрузка на контур — 12 000 RPS суммарно + 30 % запас; добавочная латентность шлюза p99 ≤ 15 мс |
| NFR-04 | Лимиты на пару «потребитель → поставщик» по профилям: «Базовый» 50 r/s, «Повышенный» 200 r/s, «Критичный» 500 r/s — превышение → отказ с кодом 429; для новых потребителей первые 2 недели — режим «только наблюдение» (dry-run) |
| NFR-05 | Защита узлов АС-поставщика от каскадного отказа при деградации группы (часть узлов выведена healthcheck) — лимит нагрузки на каждый узел группы |
| NFR-06 | Инцидентное изменение лимита конкретной пары (временное повышение или понижение на время расследования) — без перезагрузки и разрыва соединений, ≤ 5 мин, с автоматическим возвратом к исходному значению |
| NFR-07 | Плановые изменения конфигурации шлюзов — без разрыва установленных соединений АС |
| NFR-08 | Наблюдаемость по каждой паре АС: RPS, коды ответов, срабатывания лимитов — задержка данных ≤ 1 мин, выгрузка в Prometheus/Grafana банка |
| NFR-09 | Доставка access-логов и событий аудита в SIEM — ≤ 5 мин |
| NFR-10 | Масштабирование под рост до 60 АС и +25 %/год — горизонтально, без перепроектирования схемы |
| SEC-01 | TLS для всех соединений: АС-потребитель ↔ шлюз, шлюз ↔ АС-поставщик, шлюз ↔ Vault, шлюз ↔ коллектор трассировки; версии протокола не ниже 1.2, предпочтительно 1.3; plain HTTP между системами выводится из эксплуатации |
| SEC-02 | Взаимная** аутентификация на обоих стыках: потребитель предъявляет клиентский сертификат своей АС; шлюз предъявляет клиентский сертификат АС-поставщику; АС-поставщик проверяет сертификат шлюза |
| SEC-03 | Идентичность АС = уникальный сертификат на систему (CN/SAN = системный идентификатор); проверка по реестру ИБ (INF-05); wildcard- и «общие» сертификаты на группу АС **запрещены |
| SEC-04 | Закрытые TLS-ключи шлюзов **не должны храниться файлами на ВМ**; источник сертификатов — Vault банка (INF-03) |
| SEC-05 | Аудит событий идентификации (какая АС вызывала), авторизации и изменений конфигурации; выгрузка в SIEM |
| SEC-06 | Служебные эндпоинты (метрики, управление лимитами, ИИ-агент) — только из внутреннего контура управления / loopback, с TLS и ограничением по адресам |
| SEC-07 | Ротация TLS-сертификатов шлюзов автоматически, без остановки обслуживания; контроль сроков действия с оповещением |
| SEC-08 | В ответах не раскрываются технические детали (имя и версия прокси-сервера, внутренние имена узлов АС) — требование zero-trust действует и внутри периметра |
| SEC-09 | Запрет debug-уровня журналирования в промышленном контуре (допускается только штатная кратковременная диагностика) |
| SEC-10 | Весь административный доступ к ВМ шлюзов — персонализированный, через PAM (INF-06) |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

| D2 | Схема развёртывания (текстовая: Mermaid или PlantUML): сегментные шлюзы SynGX в двух ЦОД, L4 VIP на сегмент, АС-потребители и АС-поставщики, Vault, УЦ, Prometheus/SIEM, GitOps |
| D3 | Модель маршрутизации и отказоустойчивости: алгоритмы балансировки, активные healthcheck, динамический upstream по DNS, поведение при отказе узла/группы/ЦОД, fail-closed, применимость (или обоснованный отказ) sticky-сессий |

| D5 | Zero-trust сегментация и контроль доступа: матрица потребитель → поставщик, enforcement на шлюзе, разграничение ролей SynGX и МЭ, служебные эндпоинты |

| D7 | Наблюдаемость, аудит, трассировка: pull-модель метрик, состав метрик под NFR-08, access/audit-журналы в SIEM, сквозная трассировка вызовов между АС |
| D8 | Эксплуатация и жизненный цикл конфигурации: GitOps, reload и случаи, когда reload недостаточен, подводные камни Vault-интеграции, обновления, runbook |
| D9 | Таблица трассировки требований → решения |
| D10 | Реестр допущений, рисков, открытых вопросов (в т.ч. ГОСТ-TLS) и отвергнутых альтернатив |

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | SynGX представлен как **service mesh** или API-шлюз/API-management: ему как **встроенные факты продукта** приписаны функции, которых нет в документации, — sidecar-прокси, control plane (централизованная выдача идентичностей/политик), автоматический mTLS «между всеми сервисами», портал разработчика, каталог API, авторизационный сервер OAuth2, WAF, биллинг |
| HF-02 | Заявлено, что SynGX **сам** отправляет метрики во внешние системы (push) или пишет логи напрямую в Kafka «из коробки» |
| HF-03 | HA решён «встроенной кластеризацией SynGX» (межинстансовый VRRP/keepalived/синхронизация состояния как функция продукта) без явной пометки, что это внешнее решение; либо топология с единственной точкой отказа на уровне сегментного шлюза при NFR-01 |
| HF-04 | Закрытые TLS-ключи шлюзов хранятся файлами на ВМ при наличии документированного потока Vault (ключи только в shared memory) — без явного обоснования отказа и компенсирующих мер (нарушение SEC-04) |
| HF-05 | Эндпоинт горячего управления лимитами (`limit_req_change`) выставлен за пределы loopback/unix-сокета (нарушение документированного ограничения и SEC-06) |
| HF-06 | Отсутствует хотя бы один обязательный артефакт D1–D10 |

- Язык: русский; англоязычные технические термины допустимы.
