## 1. Требования, подлежащие трассировке

Всего **26** требований (INF-8, NFR-10, SEC-8).

|---|---|
| INF-01 | ЦОД-1 «Основной» и ЦОД-2 «Резервный»: ~60 км, 2×10 Гбит/с между ЦОД, RTT 1–3 мс. **Третья площадка** — облачный сегмент банка, сетево независимый от обоих ЦОД: до 3 лёгких ВМ (4 vCPU / 8 ГБ RAM / 100 ГБ SSD). | INF-02 | Под платформу в каждом ЦОД выделяется до 10 хостов: 16 CPU / 64 ГБ RAM / RAID10 NVMe 4 ТБ (XFS); ОС — только Platform V SberLinux OS Server 9.7; Java — SberJDK 17 |
| INF-03 | Развёртывание и изменения — только Ansible из корпоративного репозитория; ручные правки конфигураций запрещены |
| INF-04 | S3-совместимое хранилище развёрнуто в каждом ЦОД (раздельные бакеты, версионирование включено, кросс-ЦОД доступ есть); квота достаточна под 5-летний архив; других целей архивирования (NFS/ленты) нет |
| INF-05 | Мониторинг — Zabbix + Prometheus-совместимый сбор; SIEM принимает события по HTTPS и из лог-файлов агентами. **Platform V Monitor (COTE) в банке не развёрнут |

| INF-07 | Команда: 4 инженера middleware (Kafka — средне, Corax — базово), 1 администратор ИБ, 2 DevOps; нагрузочное тестирование перед запуском и DR-учения 2 раза в год обязательны |

| NFR-08 | Репликация не деградирует основной кластер — Дополнительная нагрузка на продюсеров/брокеров ЦОД-1 ≤ 5 % в пике |

| SEC-01 | TLS не ниже 1.2 (рекомендовано 1.3) на всех каналах, включая межкластерные связки MM2 и подключения S3-коннекторов к брокерам и хранилищу |
| SEC-02 | Аутентификация всех клиентов платформы, включая коннекторы MM2 и S3; персональный принципал на сервис; анонимный доступ запрещён |
| SEC-03 | ACL с минимальными правами на обоих кластерах; консистентность ACL между ЦОД (оценить механизм репликации ACL); запрет wildcard-административных ACL |
| SEC-04 | Аудит всех административных операций (топики, ACL, конфигурации, квоты, группы) на обоих кластерах с выгрузкой в SIEM банка |
| SEC-05 | ПДн в событиях (ФИО, PAN-маски, счета) — сквозное шифрование: администратор платформы и обладатель архива S3 не читают содержимое без ключей; ключи — в Vault банка |
| SEC-06 | Секреты в конфигурациях коннекторов — только зашифрованные; дефолтные пароли из примеров документации заменяются; 152-ФЗ: архивы с ПДн — только в контуре банка на территории РФ |
| SEC-07 | Ротация сертификатов всех компонентов (включая узлы на третьей площадке) не реже раза в год, без недоступности кластера |
| SEC-08 | Действия администраторов при DR-переключениях персонализированы и попадают в аудит (SEC-04) |

Для каждого требования в итоговом документе должна быть строка
трассировки одного из видов:

```
<ID> -> <адрес в документе>          # раздел/подраздел, где требование закрыто
<ID> -> unverifiable: <причина>      # закрыть нельзя и объяснено почему
```

`unverifiable` без причины не засчитывается: это не статус, а отказ
от трассировки.

## 3. Hard-fail (итог ограничивается)

| ID | Правило |
|---|---|
| HF-01 | Кворум координационного слоя не переживает потерю одного ЦОД: ZK-ансамбль/кворум KRaft из чётного числа узлов или из одного узла, либо весь кворум размещён в одном ЦОД, либо третья площадка (INF-01) полностью проигнорирована — **без** явного обоснования и компенсирующих мер; либо брокер Corax размещён на третьей площадке вопреки INF-01 |
| HF-02 | Corax Mirror Maker 2 назван синхронным механизмом репликации, либо заявлен RPO = 0 при полной потере ЦОД-1 (вне контекста явного «недостижимо при MM2») |
| HF-03 | Вымышленные компоненты/функции Corax поданы как факт (например: «штатный автоматический фейловер Corax между ЦОД», «Records Policy входит в Apache Kafka», «архивирование топиков в произвольное хранилище — штатная функция», «MM2 гарантирует exactly-once доставку в целевой кластер») |
| HF-04 | Как факт заявлено, что S3-бэкап сохраняет consumer offsets, либо что смещения/партиционирование в восстановленном из S3 топике совпадают с исходными (в документации не описано — только как помеченное допущение или вопрос к вендору допустимо) |
| HF-05 | Отсутствует хотя бы один обязательный артефакт D1–D10 |
